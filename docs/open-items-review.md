## §2-bis. `CF-DUP-3` EXPLAINED — AND WHY THE IMPLEMENTED READING IS THE PRINCIPLED ONE

**THE CORNER, CONCRETELY.** `deliver` matches a trigger's ids to the registered functions and dedups per distinct identity by adding each matched id to a `Set` **before** the registry lookup, so an id whose second element stands later in the SAME `triggered` array is skipped. **The corner is what happens if, *during* that delivery, the set of registered functions changes:** a listener's own body can call the package's `register` (the closure holds the instance), so an identity whose function was absent at the first element can gain one before the second element is reached. **The question `§2.4`'s dated clause (i) does not answer: is that identity invoked at its second occurrence (the recipients re-read per occurrence), or not (the delivery's recipient set is fixed when the array is read)?** **The shipped reading: NOT invoked — the dedup is over the ARRAY's identity set, so a mid-window registration does not enter the current delivery.**

**WHY THAT READING IS THE PRINCIPLED ONE — AND THE ARGUMENT THE CONTRACT SHOULD CARRY.** **The store declares the ORDER in which `triggered` returns its members UNOBSERVABLE (no clause asserts it; the blind and live sets are forbidden from asserting it).** **A rule that made invocation depend on whether a registration happened BEFORE or AFTER the second element would therefore make an OBSERVABLE — whether the listener fires — depend on an UNOBSERVABLE (where in the array the second element happens to stand).** **That is a contradiction of the order-unobservability rule, so the alternative reading cannot hold: the only reading consistent with the rest of the contract is that a delivery's recipient set is determined from the array as it stands when the delivery begins, and a registration made during it takes effect at the NEXT trigger.** **The symmetric case behaves the same way:** a `replace` or a `unlisten` during the window changes what a LATER trigger invokes and does not reach back into the delivery in flight.

**WHAT IS STILL OWED, AND IT IS ONE LINE.** The reading is right; the CONTRACT does not yet SAY it. **The smallest repair is one clause on `§2.4`'s dated clause (i) or on `§2.12`'s registration cell: *"a registration, a replacement or a withdrawal made during a delivery window takes effect at the next trigger; the window's recipient set is read from the array as it stands when the window opens."*** **The three recorded revisit conditions stand; a `deliver` change is NOT needed, and none is recommended.**

**REACHABILITY AND SEVERITY, STATED HONESTLY:** a real caller CAN reach it (a listener body that registers), and NO cell drives it — so it is MINOR/unpinned, not a defect: the build already behaves as the principled reading requires, and the gap is documentary.
