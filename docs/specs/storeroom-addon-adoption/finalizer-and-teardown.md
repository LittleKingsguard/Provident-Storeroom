## §1. THE MECHANISM, IN ONE PARAGRAPH

**A JS instance carries a finalizer. When the instance becomes unreachable and the runtime collects it, the finalizer frees the one Rust store that instance owns.** **The client is not required to call anything**: a client that holds its reference forever leaks exactly as it does today, so **no leak becomes worse than it is now** — the finalizer only improves the case where the client lets go. **No verb is added.** `R: the TORN DOWN row.`

---

## §2. ONE CONSTRUCTION, ONE STORE, ONE JS OBJECT

**This is the finalizer's validity condition and it is verified, not assumed.**

- **`storeCreate` builds a fresh `Store` per call**, with its own handle domain. **The index beside it is a SLOT IN A LOOKUP TABLE AND NOT A STORE IDENTITY.**
- **The architect's own acceptance test:** two constructions yield **two discrete stores in separate memory**. Measured: a write at one answers `AddressNotFound` at the other, and the same handle string registered in both fires only its own body.
- **No member hands out a second store object**, so there is no state in which "the JS store" and "an instance" are different things.

**SO TEARDOWN FREES THE ONE STORE THE DELETED INSTANCE OWNS AND NO OTHER.** No store is shared between instances, so a finalizer is a lawful drop and not a partition. `[CONTRACT]`

---

## §3. THE FILE

1. **THE FILE PERSISTS AND TEARDOWN DOES NOT TOUCH IT.** **Teardown is memory, not bytes.**

2. **REOPENING IS ALREADY THE DESIGNED PATH, AND THIS IS WHY THE FILE'S PERSISTENCE IS NOT A NEW PROBLEM.** The construction has two arms: when the file is **absent** it is created exclusively; **on `AlreadyExists` the construction falls through to an EXISTING WRITE-MODE OPEN**, deliberately, so that *"a construction over an EXISTING file NEVER TRUNCATES and the persisted register is never destroyed by the construction that reads it."* **So the exclusive-create flag guards CREATION and not reopening, and the persisting file is the seed of the next construction.**

3. **THE PASS THAT READ THE FLAG BY ITS NAME AND CONCLUDED REOPENING WAS FORBIDDEN WAS WRONG.** The arm answers it; read the arm, not the identifier. This is stated because the error was made and is the kind that recurs. `[CONTRACT]`

## §4. THE ACTIVE-EDIT COUNT

**The finalizer must not run mid-edit. The barrier is a per-store count of edits in flight.**

### §4.3 The structure

**A second index over the kernel's own attempt records, keyed by store.** Narrow by design: **`constraint-kernel.mjs` is refactored later**, so this index is written so that refactor is a **replacement** and not the same idea in two places.

**The attempt record ALREADY CARRIES ITS OWN `store`**, so **nothing is added to any record and no existing reader moves.** The kernel's records stay keyed by their attempt reference, as the corpus requires: a reader answers from the record and not from the store instance. **This index answers a LIFECYCLE question that reader does not ask.** **AND ITS READER IS `§4.2`'s SEAM — the two `Symbol.for` channels on the STORE INSTANCE, `Symbol.for('provident-storeroom.attempt-count')` and `Symbol.for('provident-storeroom.attempt-opened')`, added 2026-10-20 on gate-3 finding `2` and RECONCILED the same day from a module export to a store-keyed channel so that `constraint-kernel.mjs`'s six-name export set is untouched — which reads THIS index and no record member, so this clause's prohibition stands whole.** `[CONTRACT]`

### §4.4 The wait

**THE FINALIZER WAITS FOR ITS STORE'S COUNT TO REACH ZERO, THEN DROPS THE STORE.**

**THE WAIT IS PER STORE.** One store's teardown never blocks on another's traffic — **a process-wide wait would let a busy store starve every teardown**, which is why the index is keyed by store and not global. `[CONTRACT]`

### §4.5 What the barrier covers, and the one thing it does not

**An in-flight file edit is inside the call that opened it, so a zero count means no edit is mid-flight.** That is the file barrier, and it needs no separate mechanism.

**AND ONE READING IS FLAGGED RATHER THAN CERTIFIED.** The corpus declares the listener invocation **synchronous, and after the addon's call has returned**. **So a delivery downstream of an edit completes inside the window that edit holds, and a zero count is read as sufficient.** **The thing this count CANNOT see is a listener body that outlives its triggering write**; the synchronous declaration is the only ground for saying it cannot. **A pass that measures otherwise owes a correction to the ruling row, not to this part.** `[CONTRACT]`

## §5. THE OWNERSHIP CHANGE

**THE STORE MOVES FROM A VEC SLOT TO PER-OBJECT OWNERSHIP.**

**WHY, STATED AT ITS GROUND:** the instance table is a vector. **A vector cannot lose one element without either SHIFTING LATER ENTRIES — which would silently re-point store #2's calls to store #3 — or holding a TOMBSTONE, which grows unboundedly and defeats the teardown it exists to serve.** **Neither is acceptable, so the store is owned by the object that names it.**

**AND THIS CHANGE IS SHARED WITH THE SURFACE UNIT.** That unit removes the integer index; this unit gives the store an owner. **The two converge on the same structure**, and a landing that does either without the other leaves half a model.

**THE FINALIZER'S SURFACE IS THE LIBRARY'S**, which supplies a finalizer hook on an object. **The exact signature is the supervisor's measurement and is disclosed as such** — the crate's source is not in this tree and the lock is uncommitted, so it cannot be read here. **`STEP 0` PASS 2 closes the row against the artefact.** `[OWED]`
