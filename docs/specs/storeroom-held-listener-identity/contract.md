### §2.1 `HL-1` — THE IDENTITY IS A CALLER-SPELLED STRING, AND ITS DOMAIN IS THE STORE'S

1. **THE TYPE.** **A handle IS a `string`.** **The caller spells it, holds it and passes it back; nothing mints it.** **No counter, no UUID, no scalar and no skip loop exists** (`P: docs/pending.md · P-6`, the ruling on minting, verbatim: *"You don't need to mint anything. 2. **WHERE THE IDENTITY LIVES, AND THE TWO FABRICATIONS IT RETIRES.** **THE IDENTITY LIVES IN THE STORE, NOT IN A JS CACHE** (`P: docs/pending.md · (AA-2)`, verbatim: *"Move the identity into the store"*). **What this retires, named at its own bytes: `state.tokens` (`bindings/js/index.mjs:1984`) and its read at `:2503`; `Object.freeze({})` at `:1757`; `wrapHandles` (`:1746-1780`); and `encodeHandle` (`:1483-1488`).** **A JS cache is therefore LOAD-BEARING FOR NOTHING, and a cache miss is no longer indistinguishable from a removal, because the identity's presence IS a store row's presence** (`P: docs/pending.md · (AA-2)`, item (ii)). `[CONTRACT]`

### §2.2 `HL-2` — `listen(handle, addresses)`: TWO POSITIONS, THE SECOND A SET

1. **THE SIGNATURE AND THE ARITY FIGURE.** **`listen(handle, addresses)` — arity `2`, position `1` a `string` in `HL-1`'s domain, position `2` a SET of addresses.** **The arity figure moves `1 → 2` at FOUR declared sites, each needing its own dated clause: `docs/specs/storeroom-js/surface.md:1056` (the verb table), `:1071` (*"SOUND: 1, one position"*), `:1590` (the migration table) and `:1605` (the signature sketch); plus `bindings/js/index.d.ts:497` and `bindings/js/index.mjs:2016`, and `PAR-JS`'s row for the verb in `parameter-semantics.md`** (`P: docs/pending.md · P-6`, the ruling *"`listen` gains a handle position"* and its own consequence list; the same ruling's `(A)` clause). `[CONTRACT]`
2. **THE SECOND POSITION'S DOMAIN IS A SET, AND THE SET-POSITION CLASS TEST IS A NEW DECLARED FORM.** **`addresses` is an ARRAY of addresses, each in the store's own address domain; THE EMPTY ARRAY is IN the domain; a SINGLE address supplied as a bare array-of-segments is NOT — the position is a set and a segment list is a different shape** (`P: docs/pending.md · P-7`, the ruling *"Make listeners/constraints accept multiple addresses on creation"*, verbatim; read with its own consequence (ii): *"A SET-POSITION CLASS TEST IS A NEW DECLARED FORM — an `Address` vs `Address[]` discriminator, with its own outside-value set at `§2.5` item 5, and `PAR-JS-5`'s address row gains a set arm"*). **The outside-value set of the set position is: ABSENT · `null` · `undefined` · a non-array · an array carrying a member outside the store's address domain · an array carrying a nested array-of-arrays that is not itself an address.** **The declared answer for every one of them is the surface's ONE thrown form with the store's own code** — `AddressMalformed`, carried verbatim with the generator's own message. `[CONTRACT]`
3. **THE SET IS AN ASSIGNMENT, NOT A UNION.** **`listen(h, S2)` after `listen(h, S1)` DESTROYS `S1` WHOLLY AND INSTALLS `S2`.** **A caller cannot narrow a live handle's standing by omitting an address it previously named; the handle's standing is ALWAYS the last act's set, never cumulative** (`P: docs/pending.md · P-6`'s ruling `(R1)`, verbatim: *"S1 gets purged wholesale, yes"*). **AND `listen(h, S1)` then `listen(h, S1)` IS IDEMPOTENT ONLY IN EFFECT — purge then reinstall the same set — and never by a fast path** (`P: docs/pending.md · (R1)`, its own closing sentence). `[CONTRACT]`
4. **THE ORDER: PURGE, THEN INSTALL, AND NO INTERMEDIATE STATE IS OBSERVABLE.** **The purge of every entry the handle names runs BEFORE the install of the new set, so no observable instant holds both** (`P: docs/pending.md · (M-1)`, verbatim: *"AND IT PRECEDES THE INSTALL SO NO INTERMEDIATE STATE IS OBSERVABLE"*; `P: docs/pending.md · P-6`'s rule 2 (b)). **The store-side operation is a `Home` method BESIDE `mint`/`withdraw`/`adopt`** — **its NAME, its ANSWER (a removed-count or `()`) and its position are three naming questions the ruling leaves to this directory, and this contract DECLARES them as `DECLARED-DEFAULT`:** the name is **`purge`**; the answer is **the count of entries removed, `usize`** (so a drive can assert the wholesale reach numerically, and so the operation is NEITHER `withdraw`'s `bool` NOR `adopt`'s `()`); the position is beside them at `src/store.rs:363-490`. **`alt` priced: an answer of `()`** — priced: it makes the wholesale reach unobservable to the store's own suite and forces every drive to assert it through a later `triggered` read, which is a second-order observable for a first-order fact. `[DECLARED-DEFAULT]`
5. **THE THREE STATES AND THE ONE TRANSITION OF THE ENTRY.** **(a) `listen(handle, addresses)` WRITES THE ENTRY WITH `off` SET** — the reservation; **(b) `register(handle, listener)` CLEARS `off` AND INSTALLS THE FUNCTION**; **(c) `removeListener(handle)` REMOVES THE ENTRY WHOLE, and it is the ONLY route that removes one** (`P: docs/pending.md · P-5`, the ruling ***"Add an explicit delete."*** read with *"handle-with-no-function is not a valid state. Unlisten reserves its token by keeping it in the map with a property declaring it is off."* and the ruling *"Check on/off at the time of decision whether to add the function to the recipients list, not at runtime."*). **SO AN ENTRY WITH NO FUNCTION IS NOT A LAWFUL VALUE, and the state `listen`'s own return once created — a handle the caller holds with no function yet — is modelled as an entry that EXISTS AND IS OFF, which is exactly what ruling (a) provides** (`P: docs/pending.md · P-5`, the ruling on the entry's shape). `[CONTRACT]`
6. **THE BOUND ON THE MAP'S SIZE, AND ITS AUTHORISING CLAUSE.** **The map's size is bounded by the set of handles the caller has LISTENED TO AND NOT EXPLICITLY DELETED** — no longer by a mint, and no longer unbounded by construction, because `removeListener` removes the entry whole (`P: docs/pending.md · P-5`, its own bound clause; `A3`'s `A3` finding — the leak is transformed, not dissolved). **The authorising clause is `A117` (D6)'s *"released with the instance and by nothing else"* read WITH `§2.7` item 1's delete: the growth is compatible with the letter of the retention rule and bounded by the ONE route that removes an entry** (`A: docs/decisions.md · A117` (D6)). `[CONTRACT]`
7. **`listen` GAINS NO CONFLICT TEST AT ALL, AND ITS PURGE REACH IS UNCONDITIONAL.** **`listen` does not test whether the entry it destroys belongs to another actor, and no clause exempts a kernel-held entry** (`P: docs/pending.md · (C-1)`, verbatim: *"`listen` PURGES AND SUCCEEDS, and THE CONFLICT FIRES IN ONE DIRECTION ONLY — AT `addConstraint` AT AN ADDRESS A LISTENER IS ALREADY REGISTERED AT"*; `P: docs/pending.md · (C-2)` item (iv), verbatim: *"`listen` gains NO conflict test at all, and its purge reach stays unconditional"*). **THE DECLARED CONSEQUENCE OF THAT REACH, PRINTED BECAUSE IT FOLLOWS FROM *"EVERYTHING"* AND IS THE RULING'S OWN OUTCOME: the store's home entry is PER ADDRESS and the kernel's `noopListener` registration is SHARED by every pair at that address, so A WRITE TO ONE PAIR AT AN ADDRESS SILENCES DELIVERY FOR EVERY PAIR THERE** (`P: docs/pending.md · (Y-1)`, its declared consequence; `docs/specs/storeroom-constraints/kernel-surface.md §2.2` item 4 — *"`n` pairs at one address are `n` registry rows over ONE store entry"*). **The pair STILL EVALUATES, because `evaluate` reads the registry and not the store** (`§2.8` item 5). `[CONTRACT]`

### §2.3 `HL-3` — A WRITE TO A HELD PAIR: VALIDATE, THEN PURGE, THEN ADD

1. **THE RULE, IN THE RULING'S OWN WORDS.** **A constraint written to an existing handle PURGES EVERYTHING OF THE OLD HANDLE, THEN ADDS THE NEW ONE.** *"Everything, no exceptions, stop inventing ones. Override all conflicting decisions."* (`P: docs/pending.md · (O-3)`, quoting the architect verbatim; `P: docs/pending.md · P-5`'s item 1.4 ruling, the same words). `[CONTRACT]`
2. **THE ORDER: VALIDATE → PURGE → ADD, AT EVERY SITE THAT REACHES `K-1` FROM A HELD PAIR.** **The four sites, named: `addConstraint`'s overwrite arm (`bindings/js/index.mjs:3042-3052`); `constraintOn`; `constraintOff`; and the construction's `cfg.constraints` batch (`:2076-2096`)** (`P: docs/pending.md · (O-4)`, its item (iii), verbatim: *"THAT THE ORDER IS CHECK → PURGE → ADD at every site that reaches `K-1` from a held pair"*). **AND THE GUARD THE ORDER IS: a purge that runs before the new element is known-good destroys the old listener and then fails to install, leaving the address bare — a purge with no add** (`P: docs/pending.md · (O-4)`, its own ground; `A: docs/decisions.md · A76`, the validate-first rule this is an instance of). `[CONTRACT]`
3. **THE CHECK'S FAILURE LEAVES THE OLD HANDLE WHOLE, AND THAT IS NOT AN EXCEPTION.** **The exception to *"no exceptions"* is not a second case but the ABSENCE of a purge, since nothing was ever purged** (`P: docs/pending.md · (O-4)`, its item (ii), verbatim). **The observables: the old listener still stands at every address it stood at; its function still fires; `constraints()`'s return is unmoved; and the call threw.** `[CONTRACT]`
4. **WHAT *"A VALID CONSTRAINT CREATION"* IS CHECKED AGAINST — THE SPLIT, ENUMERATED BECAUSE THE PROPOSAL OWES IT AND THIS CONTRACT CARRIES IT.** **PRE-CHECKABLE BEFORE THE PURGE, four classes:** **(i) a non-function `constraint`** — `KC-2` (`bindings/js/src/constraint-kernel.mjs:378-383`), and `PAR-JS-22` at `bindings/js/index.mjs:2915-2917`; **(ii) a malformed pair or a non-string `id`** — `constraintSite` (`bindings/js/index.mjs:2902-2917`); **(iii) an address outside the store's domain** — `KC-1` (`bindings/js/src/constraint-kernel.mjs:372-377`); **(iv) the pair's shape and its two members** — `constraintSite`'s own plain-object and `hasOwn` tests. **NOT PRE-CHECKABLE, and these produce the failure the order exists to prevent: registration-time EVALUATION (state 2, `registrationEvaluation` at `bindings/js/src/constraint-kernel.mjs:503-516`), state 3's attempted repair, the store's own refusal of `listen` (channel (ii)), and `register` on a purge-emptied bucket** (`P: docs/pending.md · (X-4)`, its own enumeration, verbatim). **SO THE ORDER CANNOT DELIVER *"a purge with no add is impossible"* FOR THE FOUR ROWS THAT MATTER: a state-2 or state-3 failure at a held pair still purges first and refuses after** (`P: docs/pending.md · (X-4)`, its own conclusion). **THIS CONTRACT RECORDS THAT CONSEQUENCE AS DECLARED AND NOT AS A DEFECT: the pre-check's reach is the four pre-checkable classes, and the post-purge refusal's residue is declared at `§2.3` item 6.** `[CONTRACT]`
5. **WHAT *"A VALID CONSTRAINT CREATION"* MEANS, AND THE DOMAIN THAT GOVERNS IT.** **The term is NOT defined in the corpus as one thing: `docs/specs/storeroom-native/contract.md §7.3` (b) calls it a REGISTRATION; `§8.1` #16's trigger calls it a VALIDATION OF THE LOADED STATE; and `PAR-JS-21` calls a functionless pair *"well-formed and admitted"*** (`P: docs/pending.md · (X-4)`, its closing sentence). **THE GOVERNING DOMAIN THIS CONTRACT DECLARES: the check is `KC-1`'s address domain, `KC-2`'s class domain and `constraintSite`'s pair-shape domain, taken TOGETHER — i.e. the four pre-checkable classes of item 4 — and NOT the store-side loaded-state validation, which is a different instant** (`A: docs/specs/storeroom-native/contract.md §7.3` (b) and `§8.1` #16, cited and re-derived nowhere here). `[CONTRACT]`
6. **THE PURGE-THEN-ADD'S RESIDUE, DECLARED AT THE SITES THAT REACH IT.** **At `addConstraint`'s overwrite arm the try/register/catch order (`bindings/js/index.mjs:3045-3049`) means a refused registration leaves the held element *"EXACTLY AS IT STOOD"* — the entry's record is written only after the registration returns** (`bindings/js/index.mjs:3043-3044`; `docs/specs/storeroom-js/surface.md §2.12` item 3's *"NO identity is returned and NO element is carried"*). **THE CHANGE THIS ITEM CARRIES IS THEREFORE STATED EXACTLY: the JS ENTRY's standing is already protected by that ordering; what the purge ruling adds is that the STORE's entries are purged BEFORE the registration is attempted, so a state-2 or state-3 refusal at a held pair DOES destroy the store-side listener and leave the JS entry standing.** **THE OBSERVABLE CONSEQUENCE, DECLARED: after such a refusal the pair still EVALUATES and its delivery resolves to nothing silently** — the same declared outcome `(D-vi)` already carries (`P: docs/pending.md · (D-vi)`; `§2.8` item 5). **AND THE REPAIR ROUTE FOR THAT STATE IS `removeConstraint` THEN `addConstraint`** (`P: docs/pending.md · (F-2a)`, verbatim: *"remove constraint if it exists, then add new one"* — and its order is the rule). `[CONTRACT]`
