## §1. The pair, member by member

**THE ARCHITECT'S GROUND, VERBATIM: *"Make the store include the address when passing a trigger so that a constraint/repair/listener can know where a multi-address handler was fired."*** (`P: docs/pending.md · P-7`, verbatim).

### §1.1 The `handle` member

**The subject.** **`handle`** — the store's own adopted identity for the listener that fired. **Its `unit`** is unitless. **Its `domain`** is the store's own handle domain: a non-empty `string` (`identity-and-domain.md §2`), never a wrapper and never a token. **Its `referent`** is the listener entry the store holds. **Its `evaluator`** is **store-side for the selection and caller-side for the match** — the store names it and the package resolves it against its own `registry`. **Its `observable`** is the value a listener's invocation is keyed by and the value the dedupe keys on. **Its clause** is `contract.md §2.4` item 1 and `parameter-semantics.md §2.19` (`PAR-HL-19`). `[CONTRACT]`

### §1.2 The `address` member — the BINDING address

**The subject.** **`address`** — `listener.address`, THE BINDING'S OWN ADDRESS. **Its `unit`** is unitless — a segment list. **Its `domain`** is the store's own address domain. **Its `referent`** is the address the listener was BOUND at, which is the address the prefix test matched and is a PREFIX OF, or equal to, the written address. **Its `evaluator`** is **store-side**: it is available at the selection site inside the filter (`src/store.rs:1723-1724`) and is today DISCARDED by the `.map(|listener| listener.handle.clone())` on the next line (`:1724`). **Its `observable`** is the `address` member of every element of `triggered` and of `pending`, and the fact that it DIFFERS from the invocation's argument wherever the binding is a strict prefix. **Its clause** is `contract.md §2.4` item 7 and `parameter-semantics.md §2.20` (`PAR-HL-20`). `[CONTRACT]`

### §1.3 Why the pair is needed at all — the prefix rule's own terms

**THE SELECTION RULE IS PREFIX AND DESCENDANT-INCLUSIVE — `triggered_for` filters `is_prefix(&listener.address, address)` (`src/store.rs:1718-1726`; `docs/specs/storeroom-native/write-and-read.md §6.5` item 10 (d) (iii); `A33`/`A37`; `DD-18`) — so A LISTENER BOUND AT `['a']` FIRED BY A WRITE AT `['a','b','c']` IS TOLD `['a','b','c']`, and the binding it fired through is recoverable today ONLY by the caller re-running the prefix test itself** (`P: docs/pending.md · P-7`'s defect clause, verbatim). **AND THE MOTIVATION LEADS WITH THE PREFIX TEST AND NOT WITH MULTI-ADDRESS, on `role_critique`'s finding E3: the pair's real justification is the descendant-inclusive rule, where a listener at `W` fired by a write at a descendant `X` currently cannot tell `W` from `X`** (`P: docs/pending.md · P-7`'s review finding (5), verbatim). **AND ONE THING THE PAIR DOES NOT BUY, RECORDED SO `P-7`'S OWN JUSTIFICATION IS NOT OVER-READ: with dedupe on handle a multi-address handler FIRES ONCE, its one argument is the WRITE's address, and WHICH BINDING MATCHED IS THE OUTPUT OF AN UNORDERED ITERATION — so the architect's stated purpose is not served by the pair list FOR THE LISTENER CONSUMER, and that finding stands recorded for the proposal pass** (`P: docs/pending.md · P-7`, the fifth finding's clause, verbatim: *"THE ARCHITECT'S STATED PURPOSE … IS THEREFORE NOT SERVED BY THE PAIR LIST AS RULED for the LISTENER consumer"*). `[CONTRACT]`

## §3. `pending`: the seeding clone, the pop, and the total element type

1. **THE RULING, VERBATIM: *"Push the pair into pending. Pending is seeded as a clone of triggered."*** (`P: docs/pending.md · P-7`, verbatim). **AND `P: docs/pending.md · (AA-7)`'s fuller words: *"Pending is seeded by caching the triggered set from the store. Pop from set to check off. Pending will only store the actual still-pending steps."*** **SO `pending` INHERITS WHATEVER SHAPE `triggered` CARRIES, WITH NO SECOND EDIT AT THE SEEDING SITE.** `[CONTRACT]`
2. **THE SEEDING IS VERIFIED AT THE BYTES AND IS A CLONE, NOT A TRANSFORM.** **`bindings/js/src/constraint-kernel.mjs:891` is `record.pending = written.triggered.slice();` — a member-for-member copy of the SAME element identities — and the comment at `:886-888` says so: *"the write's returned set is then written into `triggered` and into `pending` AS ONE LIST, member for member and by the SAME handle identities"*. `:1288`'s attempt record seeds the same way (`attempt.record.pending.slice()`) and `:575`'s repair context does too** (`bindings/js/src/constraint-kernel.mjs:575`, `:891`, `:1288`; `P: docs/pending.md · P-7`'s seeding clause, verbatim). `[CONTRACT]`
3. **THE ELEMENT TYPE IS TOTAL AND THERE IS NO UNION.** **Under POP the entry is REMOVED, so nothing is carried beside `pending` and the bare-handle union has no subject** (`P: docs/pending.md · (AA-7)`, verbatim). **THE TWO SITES THE UNION USED, EACH NAMED FOR DELETION: `releasePending`'s push into `checkedOff` (`bindings/js/src/constraint-kernel.mjs:1428`, `:1431`) and the terminal arm's re-append of bare handles (`bindings/js/index.mjs:2694-2698`)** (`P: docs/pending.md · (AA-7)`, verbatim). **AND THE THIRD SITE THAT CARRIED THE UNION IS NAMED WITH THEM: `publishCheckedOff` (`bindings/js/src/constraint-kernel.mjs:1449-1458`), which publishes `attempt.checkedOff` under the `CHECKED_OFF` symbol for the terminal arm to resolve — under POP it publishes nothing** (`contract.md §2.4` item 5). `[CONTRACT]`
4. **AND THE OWED FIRING IS UNMOVED — THE ONE THING POP DOES NOT TAKE.** **`A117` (D5)/(D6) already holds that an owed firing's home is THE REGISTRY'S RESOLUTION OF ITS IDENTITY, so a popped identity's firing is still reached** (`P: docs/pending.md · (AA-7)`, verbatim; `R: docs/decisions.md · A117` (D5)/(D6)). **THE OBSERVABLE: after a check-off pops an identity from `pending`, the delivery still resolves that identity against the package's `registry`, so a body with a function registered still runs** (`docs/specs/storeroom-js/surface.md §2.7` item 7 (a)). `[CONTRACT]`
5. **THE ONE THING THE POP CHANGES IN A DRIVE'S ARITHMETIC, PRINTED SO IT IS NOT READ AS A REGRESSION.** **`pending`'s size at any instant after a pass is the number of STILL-PENDING steps, and never the returned set's size; a drive that asserts the returned set's size against `pending`'s size AFTER a pass has asserted the pre-POP reading** (`P: docs/pending.md · (AA-7)`; `docs/specs/storeroom-constraints/kernel-surface.md §2.1` item 2's `pending` clause, cited and re-derived nowhere here). `[CONTRACT]`

## §4. The three identity comparisons, each re-spelled to compare a member

1. **THE RULE, VERBATIM: *"both filters become PAIR-AWARE — they compare `entry.handle`, never `entry`"*** (`P: docs/pending.md · P-7`'s `pending` ruling, item (2), verbatim). **THE TWO SITES:**
   **(i) `releasePending`'s `record.pending = record.pending.filter((h) => h !== handle);` (`bindings/js/src/constraint-kernel.mjs:1430`) — under pair elements the comparison is `(e) => e.handle !== handle`.**
   **(ii) the discard's `attempt.record.pending = attempt.record.pending.filter((h) => !returnedSet.includes(h));` (`:1541`) — under pair elements the comparison is against the pairs' `handle` members on both sides.**
   **AND THE FAILURE MODE EACH WOULD HAVE, STATED SO ITS ABSENCE IS THE DRIVE: with pair elements the as-built filters compare a pair to a handle and are ALWAYS TRUE / ALWAYS FALSE respectively — the check-off and the discard would silently stop removing anything** (`P: docs/pending.md · P-7`'s `pending` ruling, item (2), verbatim). `[CONTRACT]`
2. **AND NO THIRD IDENTITY COMPARISON EXISTS.** **`releasePending` and the discard are the whole set, and a `grep` for `!==`/`includes` over `pending` is the check** (`P: docs/pending.md · P-7`'s `pending` ruling, item (2), verbatim). **THIS CONTRACT PRINTS THE SEARCHED SET AT THE BYTES THIS PASS READ: `bindings/js/src/constraint-kernel.mjs`'s `pending`-touching comparisons are `:1430` and `:1541` and no third; `bindings/js/index.mjs`'s are `:2694-2699`'s `triggered.includes(handle)` over the terminal arm's list, which is a comparison over a list the POP retires.** **A third comparison appearing in a later tree is a FINDING under this item.** `[CONTRACT]`
3. **AND THE OBSERVABLE EACH RE-SPELLING IS JUDGED BY, IN THE RULING'S OWN WORDS.** **The failed-write arm's *"zero bodies of that write's own set run"* and the check-off's *"every occurrence of that identity gone"*** (`P: docs/pending.md · P-7`'s `pending` ruling, item (2), verbatim). `[CONTRACT]`

## §5. The dedupe: `entry.handle`, and the argument's own rule

1. **THE RULING, VERBATIM: *"Dedupe on handle — rule 3 stands"*** (`P: docs/pending.md · P-7`'s dedupe ruling, verbatim). **`docs/specs/storeroom-js/surface.md:309`'s *"A LAWFUL DUPLICATE FIRES ONCE PER DISTINCT HANDLE"* SURVIVES UNMOVED** (`P: docs/pending.md · P-7`'s dedupe ruling, verbatim). `[CONTRACT]`
2. **THE SITE AND THE FIX.** **`bindings/js/index.mjs:2359-2365`'s `matched.has(handle)` was keyed on the ELEMENT, and under pairs a handle at `['a']` and `['a','b']` both prefix-match a write at `['a','b','c']` — two pair objects, so the function would fire TWICE, breaching the rule. THE FIX IS THE DEDUPE'S KEY: `matched` keys on `entry.handle`, never on `entry`** (`P: docs/pending.md · P-7`'s dedupe ruling, verbatim). **`recipients.push` still pushes one entry per distinct handle.** `[CONTRACT]`
3. **THE OPERATIVE RULE, AND NOTHING BESIDE IT: THE CARRIED `address` IS SOME ONE OF THAT HANDLE'S BINDING ADDRESSES, AND A DRIVE ASSERTS MEMBERSHIP ALONE.** **The carried `address` of a handle present at several bindings is SOME ONE OF that handle's binding addresses, and THAT IS ALL — no position, no tie-break, no priority and no rank is declared, because `triggered`'s order is UNSPECIFIED (`DD-37`, `DD-22`, `docs/specs/storeroom-js/surface.md §2.7` item 3) and a rule selecting a member by iteration position would print an order claim `DD-37` forbids** (`A: docs/specs/storeroom-native/contract.md`'s `DD-37` — an asserted order *"would need `ListenerEntry` to carry a monotonic ordinal"*; `DD-22`; `P: docs/pending.md · P-7`'s dedupe ruling, its own obligation). **AND A DRIVE MAY ASSERT MEMBERSHIP ALONE: the carried `address` is a MEMBER OF that handle's own binding set, and the assertion is exactly that membership — a drive that asserts WHICH binding's address is carried, or asserts it against the list's position, asserts a wording this contract does not print** (`§5` item 4's *"INFORMATIONAL DATA ABOUT THE TRIGGER SET"*; `contract.md §5.5`'s `S-DEDUPE-HANDLE`/`S-DEDUPE-ARG`, which assert one invocation and the argument and never the carried member; `§8` `TF-2`, whose row is narrowed by its own dated clause to match). `[CONTRACT]`
