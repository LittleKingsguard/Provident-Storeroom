## §3. The snapshot, materialised without an index

1. **THE RULE.** **`evaluate`'s `standing.slice()` (`bindings/js/src/constraint-kernel.mjs:1148-1149`) is what implements `CX-12`'s *"the pass's evaluated set is FIXED WHEN THE PASS BEGINS"* (`docs/specs/storeroom-constraints/attempt-lifecycle.md §2.4` item 5 (iv)). WITH NO INDEX TO SLICE, THE SET IS MATERIALISED ONCE AT PASS START FROM `attempt.address` AGAINST `kernel.pairs`, and that materialised list is the snapshot `evaluate` and `registrationRerun` both read — so `CX-12` still holds and `K-1`'s mid-pass append still enters the NEXT pass** (`P: docs/pending.md · R-B3`, verbatim). `[CONTRACT]`
2. **THE ORDER RULE, DECLARED (`HL-DD-6`), BECAUSE THE RULING LEFT IT AS A DUTY.** **The materialised list is ordered by the pair's FIRST-REGISTRATION ORDER AT THE ATTEMPT'S ADDRESS — `docs/specs/storeroom-constraints/attempt-lifecycle.md:193`'s *"clause (ii)'s first-registration order"* — PRESERVED BY THE STORE'S OWN RETURNED ORDER AND NOT BY AN INDEX'S APPEND ORDER** (`P: docs/pending.md · (M-3)`, closing sentence, verbatim: *"it RETIRES THE ORDER LOSS `(R-B3)` INTRODUCED: `attempt-lifecycle.md:193`'s … is preserved by the store's own returned order, not by an index's append order"*). **`alt`, priced: DECLARE THE GLOBAL INSERTION ORDER OF `kernel.pairs`** — priced at the ruling's own cost note: a scan yields GLOBAL insertion order ACROSS ADDRESSES, and `withdrawRegistration`'s `pairs.delete` + re-`register`'s re-insert (`:463`, `:402`) moves a pair to the Map's tail, so a re-registered pair would change the PASS'S ORDER and not merely its membership (`P: docs/pending.md · (R-B3)`, verbatim). **Reversal point: a bounded amendment.** `[DECLARED-DEFAULT]`
3. **AND THE ONE OBSERVABLE THE ORDER IS ASSERTED BY.** **The pass's `constraint-check` entries (`docs/specs/storeroom-constraints/kernel-surface.md §2.5` item 1's `constraint-check` row) stand in the pass's order, and a drive reads THAT list and not the registry's own order** (`docs/specs/storeroom-constraints/attempt-lifecycle.md §2.4` item 5 (ii)). `[CONTRACT]`
4. **AND THE ONE RULING THE ORDER MUST NOT BREACH.** **`CC-7`'s third limb — *"a NEW pair is appended AFTER every pair already standing at that address"* (`docs/specs/storeroom-constraints/kernel-surface.md:159-161`) — IS X-3'S SEVENTH OVERRIDE: A RE-ADD UNDER PURGE-THEN-ADD IS A NEW APPEND, so the pair moves to the address's TAIL and `CC-7`'s no-re-ordering promise becomes a RELOCATION, not a deletion** (`P: docs/pending.md · (X-3)`, item (vii), verbatim; `contract.md §8` item 4 (vii)). **AND `docs/specs/storeroom-constraints/attempt-lifecycle.md:193`'s MID-PASS CLAUSE IS X-3'S EIGHTH: it reads *"a `K-1` that returns during a pass appends a pair to the registry WITHOUT appending any entry to that pass … the new pair enters the NEXT pass's set"*; under the purge-then-add the new pair is appended AND the old row is DELETED, so `evaluate`'s snapshot (`:1148-1149`, `:1166-1167`) under-counts — DELETION IS NOT APPEND, and the mid-pass purge NEEDS A DECLARED ARM** (`P: docs/pending.md · (X-3)`, item (viii), verbatim; `contract.md §8` item 4 (viii)). `[CONTRACT]`
5. **AND THE ARM THIS CONTRACT DECLARES FOR IT, since the ruling requires one.** **A PURGE DURING A PASS CHANGES THE REGISTRY AND NOT THE SNAPSHOT: the pass's evaluated set is the set materialised when it began, so a pair purged mid-pass is still evaluated by THAT pass — its row stands in the snapshot — and a pair ADDED mid-pass enters the NEXT pass's set and no earlier one.** **The count rule therefore holds exactly as `attempt-lifecycle.md:193` states it, and the absence of a `constraint-check` under-count is the observable: the pass's entries number the snapshot's size and never fewer** (`P: docs/pending.md · (X-3)` item (viii); `P: docs/pending.md · R-B3`'s snapshot clause). `[CONTRACT]`

## §4. The replaced membership test and the structural comparison

1. **`KC-7`'S REFUSAL STILL FIRES AND ITS MECHANISM MOVES.** **`kernel.held.has(token)` (`:778`) is replaced by a STRUCTURAL comparison of the attempt's address against the live attempts' addresses; `kernel.held` itself may be deleted with `addressToken`'s site (v), and THE RECORD MUST NOT LOSE THE REFUSAL** (`P: docs/pending.md · (M-3)`, item (iii), verbatim: *"`KC-7`'s refusal still has to fire, and the record must not lose it"*). `[CONTRACT]`
2. **AND THE REFUSAL'S DECLARED OBSERVABLES, WHICH ARE WHAT A DRIVE ASSERTS — NEVER THE MAP THE MEMBERSHIP CAME FROM.** **(i) a SECOND `K-2` AT A HELD ADDRESS IS REFUSED `KC-7` BEFORE THE WRITE VERB IS REACHED; (ii) a SECOND `K-2` AT AN ADDRESS WHOSE EARLIER ATTEMPT HAS REACHED ITS TERMINAL ARM IS LAWFUL and returns a fresh `CommitRecord`; (iii) a `K-2` AT AN ADDRESS THAT IS NOT THE HELD ONE — A DESCENDANT INCLUDED — IS ADMITTED, because THE HOLD IS TAKEN AT THE CALL'S OWN ADDRESS AND AT NO OTHER** (`docs/specs/storeroom-constraints/kernel-surface.md §2.1` item 2's hold clause, cited verbatim at its own terms; `contract.md §8` item 12). **A DRIVE ASSERTS THESE THREE AND NOTHING ABOUT `held`.** `[CONTRACT]`
3. **THE CHECKPOINT'S COMPARISON, AND THE ONE THING IT MUST KEEP.** **`addressToken(landing.address) === addressToken(attempt.address)` (`:1391`) becomes a STRUCTURAL, SEGMENT-WISE COMPARISON WITH `string` AND `number` DISTINGUISHED — the exact distinction the `k:`/`i:` prefixes carried** (`P: docs/pending.md · (M-3)`, item (iv), verbatim). **THE OBSERVABLE: a landing at `['a', 0]` and an attempt at `['a', '0']` are DIFFERENT addresses and the comparison answers FALSE; before the change the prefixes made the same distinction, so NO OBSERVABLE MOVES** (`P: docs/pending.md · (M-3)`, item (iv)). `[CONTRACT]`

## §5. The stale-handle state, and its governing clause

1. **THE FINDING, AT ITS OWN WORDS.** **After an app `listen(h, [A])` PURGES an address the kernel holds a pair at, `kernel.pairs` still stands (the constraint still evaluates) but `kernel.handles` holds a STALE handle — so `releasePending`'s resolution (`:1428`) and the check-off's identity comparison may not match what the store actually returned in `triggered`** (`P: docs/pending.md · R-B3`'s closing consequence, verbatim). `[CONTRACT]`
2. **THE GOVERNING CLAUSE IS `(D-vi)`, AND THE STATE IS DECLARED AND NOT UNREACHABLE.** **The pair's REGISTRY standing and its STORE standing are two facts, and only the registry one is the kernel's to keep; the store one belongs to the app's own listens and the kernel does not re-assert it. A PURGED PAIR STILL EVALUATES AND STILL FIRES ITS DELIVERY THROUGH THE REGISTRY, and the handle it fires under is the pre-purge handle the registry recorded — which the app's `triggered` list will not carry, so the delivery resolves to `undefined` and fires NOTHING SILENTLY. THAT SILENCE IS THE DECLARED OUTCOME AND NOT A DEFECT** (`P: docs/pending.md · (D-vi)`, verbatim; `docs/specs/storeroom-js/surface.md §2.4` rule 1). `[CONTRACT]`
3. **AND THE ONE REFINEMENT `(X-6)` REQUIRES OF THAT CLAUSE.** **Under the purge-then-add the STANDING ARM RE-ENTERS THE CREATION ACT, so the purge clears the store-side home entry and the re-add mints a fresh one; `kernel.handles.set` (`:403`) then OVERWRITES the mapping, CONTRADICTING `(D-ii)`'s *"fixed and never refreshed"* BUT LEAVING NO STALE ENTRY. SO `(D-vi)`'S DISPOSITION OF A PURGED PAIR — *"still evaluates, fires nothing silently"* — DESCRIBES A STATE THE PURGE-THEN-ADD NO LONGER PRODUCES AT `addConstraint`, ONLY AT `listen`** (`P: docs/pending.md · (X-6)`, verbatim). **THIS CONTRACT STATES THAT NARROWING.** `[CONTRACT]`
4. **AND THE ONE THING THE STATE STILL OWES AT `K-6`, RECORDED AS `OWED`.** **Whether the REMOVAL is a no-op on the stale-handle state or whether the purge is also reached from the removal is `OWED`** (`P: docs/pending.md · (M-2)`, closing paragraph, verbatim; `contract.md §10` item 4; `remove-member.md §2.9` item 7). `[OWED]`

## §6. The two consequences the deletion costs, printed so they are not discovered later

1. **THE SCAN.** **The `O(N_pairs)` scan `R-B3` forced, with a string rebuilt per row, is NOT the design — there is no scan, because the store tells the kernel which pairs stand where** — **but the SELECTION `(AA-1)` declares IS a scan over `kernel.pairs`, and its cost is per LANDING rather than per attempt** (`P: docs/pending.md · (M-3)`, its own closing, and `(AA-1)`'s accepted cost, each verbatim). **A drive does not assert a cost; a plan step prices it** (`implementation-plan.md §4`). `[CONTRACT]`

3. **AND THE ONE THING THE DELETIONS DO NOT MOVE: NO STORE SITE CHANGES FOR THE `byAddress` DELETION, NO NEW SEAM IS INVENTED, AND THE STORE IS NOT PLUMBED INTO THE KERNEL** (`P: docs/pending.md · R-B3`, verbatim). **`kernel.pairs`, `kernel.handles` and `kernel.held` are the kernel's own caller-side structures and none of them is a store member.** `[NEGATIVE]`
