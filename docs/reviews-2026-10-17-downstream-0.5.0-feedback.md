# REVIEW OF THE DOWNSTREAM `0.5.0` REPORT (2026-10-17, supervisor)

**EVERY CLAIM CHECKED AGAINST INSTALLED `0.5.0` AND THIS PROJECT'S OWN SOURCE. VERDICT: THE STRUCTURAL CLAIMS ARE ACCURATE AND TWO ARE VERIFIED AT THE SOURCE; ONE CLAIM (DEF-M's FIRST HALF) DOES NOT REPRODUCE AS DESCRIBED IN MY PROBES, WHILE ITS **SECOND HALF REPRODUCES EXACTLY**.**

## DEF-M — THE REPAIR ARM

**FIRST HALF — *"where 0.4.0 left the repaired value (1) after a repaired write, 0.5.0 leaves the rejecting one (9)"* — NOT REPRODUCED IN THE SPELLINGS I DROVE.** **Both the context-threading repair and the closure-only repair landed the repaired value (`{"v":1}`) in my probes, though each also THREW `FileCommitFailed` with *"the repair fixer produced no op at [\"k\"]"*** — **so on those spellings the repair is not silent-successful; it fails loudly and the repaired value stands.** **THE DOWNSTREAM PROJECT'S EXACT SPELLING WAS NOT REPRODUCED HERE, AND THEIR OBSERVATION IS **NOT DISPUTED** — it is recorded as unreproduced-in-my-forms, which is a different claim from refuted.**
**⟶ SECOND HALF — CONFIRMED, AND IT REPRODUCES CLEANLY: ON THE PASSING ARM A WRITE RETURNS SUCCESSFULLY WHILE THE STORE HOLDS **THE VALUE THE CONSTRAINT REFUSED**.** **Probe: seed `1`, register a constraint that returns `{message, repair}` for value `9` (the repair writing `2`), then write `9` → THE WRITE **RETURNS** A WRITE RESULT AND `read` ANSWERS `{"v":9}`.** **SO THE REPAIR IS INVOKED, THE RE-READING PASSES, THE WRITE SUCCEEDS — AND THE STORE KEEPS THE REJECTED VALUE.** **THAT IS A DATA-INTEGRITY DEFECT AND IT IS SILENT, EXACTLY AS THE REPORT SAYS: the write's contract-level outcome is unchanged while the store holds a value a constraint refused.** **AND THEIR SECOND SENTENCE IS ALSO CONFIRMED IN SUBSTANCE: a repair's op is NOT reachable on the passing arm — no log crosses on success (that is the declared bubbling scope, failure-only), so a consumer can only learn a repair ran if the write FAILED.**
**⟹ THE DEFECT CLASS IS REAL AND THE SUPERVISOR COULD NOT REACH IT BY THEIR SPELLING. IT IS FILED FOR A DRIVE TO REPRODUCE, WITH THE PASSING-ARM HALF ALREADY REPRODUCED.**

## DEF-D — THE ABANDONED ADOPTION — **NARROWED, AND THE MECHANISM IS VERIFIED AT THE SOURCE**

**THE DRAW, VERIFIED AT `bindings/js/index.mjs:2227`, IS VERBATIM AS THEY QUOTE IT:**
```js
const pending = state.withheld.size === 0 ? null : state.adopted.values().next().value;
```
**AND THE COMMENT TWO LINES ABOVE STATES THE INVARIANT IT CONTRADICTS: *"THE ONLY ADOPTION A KERNEL-DRIVEN WRITE CAN FIND IS ITS OWN"* — WITH ITS OWN REASONING: *"an entry standing in `adopted` beside a non-empty `withheld` is a second identity, which is another kernel-driven write's, and this write finds no marker of its own."*** **BUT THE CODE DOES NOT TEST THAT: it takes `adopted.values().next().value` — THE OLDEST STANDING ADOPTION BY ITERATION ORDER — AND CONSUMES IT WHATEVER ITS IDENTITY.** **SO THE COMMENT'S REASONING IS RIGHT AND THE LINE DOES NOT IMPLEMENT IT.**
**THAT IS A REAL DEFECT AND IT IS THE KIND THE REPORT DESCRIBES: an unrelated write meets a marker that is not its own.** **THEIR FIRE-COUNT OBSERVATION (four abandonments, five writes, counts `0,0,0,0,1`) WAS **NOT** REPRODUCED IN MY SINGLE PROBE — which produced `0` fires and no error — BUT THE MECHANISM IS IN THE SOURCE AT THE LINE THEY QUOTE, WHICH IS STRONGER EVIDENCE THAN A PROBE THAT DID NOT SET UP THE SAME STATE.** **THEIR OWN REPRODUCTION STANDS AND MY PROBE IS THE WEAKER INSTRUMENT HERE.**

## CLASS 3 — UNBOUNDED RETENTION — **CONFIRMED IN STRUCTURE**

**`state.adopted` AND `state.withheld` ARE STRONG `Set`s ON THE INSTANCE (`index.mjs:1945`), AND EVICTION EXISTS BUT ONLY ON SPECIFIC PATHS (`:2188`, `:2235`, `:2666`, `:2746`, `:2752`, `:2755`) — so an ABANDONED adoption with no write to consume it IS RETAINED, which is what they report.** **AND `LIVE` HAS BOTH SITES (`constraint-kernel.mjs:755`, `:1551` delete; `:869` set), SO THEIR *"`LIVE.delete` exists, its counterpart does not"* IS **NOT ACCURATE FOR `LIVE`** — but their `DEF-J` names the kernel's **CLOSED map**, which is a different structure, and THAT remains to be checked rather than assumed.**
**AND THEIR POINT ABOUT `constraints()` IS SHARP AND ACCURATE: THE READER CAN NOW ENUMERATE PAIRS FOREVER WHILE REPORTING NO EVICTION — *"which makes the absence more visible, not less."*** **THAT IS EXACTLY THE EFFECT THE NEW MEMBER HAS, AND IT IS WORTH RECORDING AS A CONSEQUENCE OF THE RELEASE RATHER THAN A DEFECT IN IT.**

## CLASS 4 — THE DECLARATION VERSUS THE BEHAVIOUR — **CONFIRMED, AND WE ALREADY KNOW THE OUTCOME**

**THEIR `DEF-K` IS THE GAP THIS PROJECT ALREADY PROBED AND **REFUTED IN ITS DOWNSTREAM FORM** (`§98`): the declaration's optional body member is CORRECT because `PAR-JS-21`'s evaluator cell forbids the package-side validation a required member would be.** **BUT THEIR FRAMING IS RIGHT AND MINE WAS TOO NARROW: the code reads an UNDECLARED SIXTH KEY (`element.constraint`) THAT THE SHIPPED DECLARATION DOES NOT TYPE, so a TypeScript consumer cannot use the batch route without a cast — AND THE DECLARATION IS TYPE-CHECKED BY NOTHING IN THE PACKAGE'S OWN SHIPPING (the type-check instrument is the REPOSITORY's, not the tarball's).** **⟹ THEIR CONCLUSION IS THE RIGHT ONE: *"a declaration that only the code knows is not a contract."*** **THE REMNANT THIS PROJECT ALREADY ROUTED — a clause declaring a SIGNAL for a body-less element — REMAINS OWED, and their evidence strengthens it.**

## DEF-O — `constraints()` IS NOT THE `R3` DELIVERY — **ACCURATE, AND THIS PROJECT OVERSTATED IT**

**THEIR READING IS EXACT: the thirteenth member returns `{address, id}` pairs — 0 ops, 0 messages, 0 state, one snapshot — and its own declaration says *"not a pending() reader, not an attempts() enumerator, not a live view of a running commit."*** **IT IS A READER FOR THE CONSTRAINT REGISTER.** **⟹ AND THE PROJECT'S OWN RECORDS CALLED IT THE DELIVERY OF THE ARCHITECT'S *"Expand the kernel list"* AND TIED IT TO `R3`.** **THE RULING'S SUBSTANCE — a client-readable registry — IS DELIVERED; THEIR POINT IS THAT `R3` IS ABOUT THE **COMMIT** REGISTER AND THIS READS THE **CONSTRAINT** ONE.** **THEY ARE RIGHT, AND THE PROJECT'S `§94`/`§95` LANGUAGE CONFLATED THE TWO REGISTERS.** **RECORDED AS A CORRECTION TO THIS PROJECT'S OWN RECORD.**

## CLASS 5 — THE RECORD VERSUS THE BYTES
