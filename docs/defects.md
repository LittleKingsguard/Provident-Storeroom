## DEF-2026-10-21-U — THE CODEC SWAP'S DECODER PARITY WAS NEVER PROVED, AND THE PROOF THE SWAP WAS BRIEFED TO GET SHOWS THE LOADER'S ACCEPTANCE SET NARROWED IN FOUR CLASSES

**WHAT THIS ROW IS.** The `serde_json` codec swap (`fc5f915`, 2026-10-21) was briefed with one condition: *"the swap is a real behavioural surface: error shape, number formatting, string escaping — it needs a parity proof, not just a compile."* **THE ENCODER HALF WAS PROVED** (the compliance review's own byte-diff: `33` of `34` parity cases byte-identical, the one difference being the two escape characters — `DEF-2026-10-21-E`; `A141`). **THE DECODER HALF WAS NEVER MEASURED, AND NO RECORD OF THE LOADER'S ACCEPTANCE SET EXISTS IN THE CORPUS AT ALL.** This row is that measurement.

**THE MEASUREMENT.** One corpus of `57` inputs, run through BOTH decoders side by side: the pre-swap hand-rolled codec (`fc5f915^:src/json.rs`, verbatim) and the shipped `serde_json` codec (`src/json.rs` at HEAD, verbatim), over the shipped `StoreValue` (`src/value.rs`, verbatim) in a scratch crate (`scratch/codec-parity/`, GITIGNORED, NOT a deliverable — rebuildable from the recipe: the two `json.rs` versions + `src/value.rs` + `serde`/`serde_json` with `float_roundtrip`; the probe prints, per case, each build's verdict and the value it decoded, the value compared by re-encoding with the PRE-swap encoder so the comparison is on the VALUE and not on either spelling). **`15` DIVERGENCES IN `57` CASES.** The corpus's own claims about the codec (`A141`'s escape image, `A142`'s number spelling, the `src/json.rs` docs) were checked against the same probe and **hold**; the divergence is in what the loader ACCEPTS, which nothing in the corpus declares.

**THE FOUR NARROWING CLASSES — the pre-swap build accepts what the shipped build REFUSES:**
1. **A RAW CONTROL CHARACTER INSIDE A STRING** (a literal `LF`, `TAB` or `NUL`): the pre-swap `parse_string`'s catch-all arm pushed any character, control or not; `serde_json` refuses an unescaped character below `0x20`, as JSON requires. **THE ESCAPED FORM (`\u0000`) IS ACCEPTED BY BOTH** — so the narrowing is the RAW form only.
2. **A NUMBER SPELLING THAT IS NOT JSON** — `01`, `+1`, `.5`, `1.` — and **A NUMBER WHOSE VALUE OVERFLOWS** — `1e400`, `1e999999999` (the GRAMMAR ADMITS THOSE TWO SPELLINGS; the VALUE is what overflows): the pre-swap `parse_number` collected the run and handed it to Rust's `f64::from_str`, which accepts all six (the two over-range ones as `inf`); `serde_json` refuses the first four as a grammar violation and the last two as out of range. **THE UNDERFLOW HALF IS NOT A DIVERGENCE AND IS NOT REFUSED: `1e-400` and `1e-324` ARE ACCEPTED AND BECOME `0` (measured), and the pre-swap's own `f64::from_str` gave the same zero — so the two builds AGREE there.**
3. **A UNICODE WHITESPACE CHARACTER AS A TOKEN SEPARATOR** (e.g. `U+00A0`): the pre-swap `skip_ws` used `char::is_whitespace` (the whole Unicode property); `serde_json` admits exactly four separators (space, tab, `LF`, `CR`).
4. **A NESTING DEPTH OF `128` OR MORE**: the pre-swap parser recursed with no limit; `serde_json` refuses at its recursion limit of `128`. **AND THE AS-FILED HALF *"THE STORE'S OWN ADMITTED CEILING IS DEPTH `64` (`crossing.md §1.4` item 5), SO NO ADMITTED VALUE IS EVER NEAR THIS LINE"* IS CORRECTED: THE `64` IS THE JS PACKAGE'S OWN WALK CEILING, NOT THE STORE'S — `docs/specs/storeroom-js/crossing.md §1.4` item 5 disclaims being the store's bound — AND THE NATIVE STORE'S ADMITTED TAXONOMY HAS NO DEPTH CLASS AND NO DEPTH GUARD AT ALL, SO THE STORE ADMITS A VALUE OF ANY DEPTH** (that is `docs/defects.md` · `DEF-2026-10-21-W`: a value of walk-depth `127` or more WAS admitted, committed as success, and lost at the next boot — and `docs/decisions.md` · `A144` puts the writer under the loader's ceiling by making the commit verify the image it writes). **THE CLASS'S SCOPE IS THEREFORE NOT *"FOREIGN FILES ONLY"*: BEFORE `A144` IT BIT ON A FILE THE STORE ITSELF WROTE, AND AFTER `A144` IT BITS ONLY ON A FOREIGN FILE** — a hand-edited one, or one written by another tool.

**AND ONE WIDENING CLASS: an ESCAPED SURROGATE PAIR** (`\uD83D\uDE00`) — the pre-swap parser's `\u` arm pushed each half through `char::from_u32`, which fails on a high surrogate, so it REFUSED every astral character written in the escaped form; the shipped decoder takes it and yields the character. **THE ESCAPED FORM IS THE ONLY FORM A FOREIGN FILE WOULD CARRY FOR AN ASTRAL CHARACTER, SO THE WIDENING IS REAL AND ONE-SIDED IN THE FOREIGN FILE'S FAVOUR.**

**WHY THE CLASS MATTERS MORE THAN IT LOOKS: A REFUSAL AT THE BOOT IS A WHOLE-FILE SILENT LOSS.** `boot_load` falls through on any decode failure and the store boots with an EMPTY register, and `storeCreate` still returns an instance (`src/json.rs`'s `decode` doc: *"the caller boots an empty store from a file it cannot read"*). **SO A FILE THE PRE-SWAP BUILD LOADED — a hand-edited file, or one written by a tool other than the store — CAN NOW LOAD AS NOTHING AT ALL, WITH NO ERROR REACHING THE CALLER.** The corpus declares the boot's answer for a PARSEABLE file whose content carries a non-admitted value (the `DD-29` clause: that key is DROPPED, the rest loads) but declares NOTHING for an UNPARSEABLE file, and the code's answer — an empty store, silently — is in a code doc only.

**WHAT DOES NOT DIVERGE, AND WHAT THE CORPUS'S CROSS-READ CLAIM COVERS.** **THE `A141` CLAIM HOLDS AS WRITTEN: "a file written by either build loads on either build" IS TRUE**, because neither build can WRITE any of the four narrowing classes — the pre-swap writer escaped every control character, wrote only Rust `Display` numbers (never a non-JSON spelling), separated tokens with ASCII spaces, and never exceeded the store's depth-`64` ceiling; the shipped writer does the same. **THE DIVERGENCE IS CONFINED TO FOREIGN FILES, AND THE CORPUS SAYS NOTHING ABOUT THOSE.**
