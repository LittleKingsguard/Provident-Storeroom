**THE THREE RULINGS AND WHAT EACH CHANGES:**
1. **THE STORE'S IDENTITY IS THE HANDLE, NOT A PRIVATE TOKEN.** Today the store mints `listener-{N}` from a process-wide `AtomicU64` into `ListenerHandle { token: String }` (`src/records.rs:165-167`; `src/store.rs:406-425`), and the JS layer wraps that token in a frozen `{}` and keeps `Map<handle, token>` to translate. **There are therefore TWO unique identities where one would do** — the store's by mint, the JS `{}` by allocation — **and the translation is lossless in one direction only, because the caller never sees the token and the store never sees the handle.** The ruling collapses them: the identity the store reports and the identity the caller holds become one value.
2. **A `listen` OVER A LIVE HANDLE REPLACES, IT DOES NOT SKIP — AND THE REPLACEMENT IS A PURGE, NOT A SECOND ENTRY.** Today `mint` **never** reuses a held token: `holds_token` answers the collision and the loop mints the NEXT one (`src/store.rs:406-411`; `DD-42` clause (1); `PAR-13`'s *"unique PER STORE INSTANCE and PER SESSION"*). **The ruling inverts the collision's disposition from SKIP to REPLACE**, and the architect's second statement of it fixes the REPLACE's reach, VERBATIM: ***"When adding a listener reusing an existing handle, purge the previous listener entirely and replace with the new one."*** **OPERATIVE READING, and it is stronger than a per-address overwrite:** **(a) ENTIRELY
**— every store entry the handle named is removed, **at EVERY address it stood at**, before the new listener is installed; nothing of the previous listener survives, and no address retains a stale entry. **(b) THE PURGE PRECEDES THE INSTALL**, so the intermediate state never holds both. **(c) THE HANDLE SURVIVES THE PURGE** — it is the identity being reused, so it is the one thing the replacement carries forward; the listener behind it is wholly new. **(d) THE CLIENT IS TRUSTED** to understand that reusing a live handle discards the listener it named, which is the ruling's own stated ground and is not to be re-litigated as a safety question at the gate. **THIS SETTLES THE FORK `P-6`'S FIRST FILING LEFT OPEN (what a replacing `listen` does to the old entry's OTHER addresses): it does not move the listener, it destroys it and installs a fresh one, so the multi-address listener is NOT the surviving shape — a handle names exactly ONE listener, standing at exactly the addresses ONE `listen` gave it.**
3. **DUPLICATES ARE NOT POSSIBLE, SO THE DUPLICATE'S DECLARED SEMANTICS GO WITH THEM** (the clause above): a handle names ONE listener; the first-match withdrawal, the `TWO HALVES READ SEPARATELY` construction and rule 3's per-occurrence counting are all consequences of a state the item removes. **AND THE PURGE SUBSUMES THEM RATHER THAN LEAVING THEM DORMANT**: with (a) above, *"THE TOKEN STAYS BOUND TO ITS REMAINING ENTRIES"* (`surface.md:800-806`) has no remaining entries to stay bound to, because no second entry under a live handle survives a `listen`.
